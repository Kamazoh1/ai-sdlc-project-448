# Design

## Context

Экран проверки доступа — компонент `src/components/App.tsx`. Он держит в `useState` выбранные `userId` и `serviceId`, строит пункты `user-select` из `config.users` и вызывает `checkAccess` из `useSimulator`, только когда выбраны оба значения. Состав групп сотрудника хранится в `User.groupIds`, список групп — в `config.groups`. Компоненты по `docs/architecture.md` получают всё через `../app` и не пересчитывают доступ сами. Мотивация — см. proposal.md.

## Goals / Non-Goals

**Goals:**

- Добавить фильтр по группе так, чтобы ответ расчёта для выбранного сотрудника не менялся.
- Обойтись без изменений в `src/domain` и `src/app`.

**Non-Goals:**

- Фильтр не сохраняется в `localStorage` и не попадает в файл экспорта.
- Не фильтруется список сервисов и не меняется `PermissionsPanel`.
- Поведение фильтра после импорта, удалившего выбранную группу, отдельно не обрабатывается (так же, как сейчас не обрабатывается удалённый импортом выбранный сотрудник).

## Decisions

### Состояние фильтра — локальный `useState` в `App`

Значение `groupId` (по умолчанию `""`) хранится рядом с `userId` и `serviceId`. Фильтр — часть интерфейса экрана, а не конфигурации, поэтому в `useSimulator` ему не место. Альтернатива — хранить в слое приложения — добавила бы состояние, которое никому, кроме экрана, не нужно.

### Список сотрудников фильтруется в компоненте по `groupIds`

Пункты `user-select` строятся из `groupId === "" ? config.users : config.users.filter((u) => u.groupIds.includes(groupId))`. Это отбор пунктов списка по членству, а не расчёт доступа: `checkAccess` вызывается как раньше и получает тот же `userId`, поэтому правило «единый модуль расчёта» не нарушается. Альтернатива — функция `usersInGroup` в `src/domain` с реэкспортом из `src/app` — оправдана, если отбор понадобится второму экрану; сейчас это одна строка в одном месте.

### Сброс сотрудника — в обработчике смены группы, а не в эффекте

В `onChange` у `group-filter`: записать новый `groupId`; если он не пуст и выбранный сотрудник в эту группу не входит, выставить `userId = ""`. Выбор «Все группы» `userId` не трогает, поэтому сброшенный сотрудник не возвращается, а оставшийся выбранным — сохраняется. Альтернатива — `useEffect`, следящий за `groupId`, — даёт лишний рендер с неконсистентным состоянием (значение `user-select` не среди пунктов) и сложнее для чтения.

### Пункты `group-filter`

`[{ value: "", label: "Все группы" }, ...config.groups.map((g) => ({ value: g.id, label: g.name }))]` — порядок групп как в конфигурации. Используется тот же `NativeSelect` из Mantine, что и для остальных списков, с подписью «Группа», размещается перед `user-select`.

## Risks / Trade-offs

- [Выбранная группа исчезла после импорта, и значение `group-filter` не совпадает ни с одним пунктом] → Вне рамок изменения (см. Non-Goals); тот же класс проблемы уже есть у `userId`. При необходимости — отдельное изменение, сбрасывающее выбор на экране после импорта.
- [Фильтрация по членству в компоненте может разойтись с тем, как членство трактует расчёт] → Оба места читают одно поле `User.groupIds`; при появлении второго потребителя вынести отбор в `src/domain`.
